## Discord findings

### High-level pattern
This is not one bug. The thread bundles several different Steam-cloud failure modes under one symptom label:
1. **Cloud files go to the wrong local path**.
2. **Cloud files land locally, but the game still cannot read them**.
3. **Downloads work, uploads fail or silently do nothing**.
4. **Conflict / pending-operation / stale change-number states are mishandled**.
5. **Users need manual recovery tools when sync is unsafe**.

### Strong direct evidence from the thread
- **Initial dev framing (2025-11-19):** Utkarsh explicitly called out three main problems early:
  1. Goldberg writing the wrong Steam ID (`U:1:` prefix)
  2. saves going to the wrong folder when no prefix is specified
  3. DLC download issues blocking save functionality for some games
- **Binding of Isaac evidence:** a screenshot (`1440859690719514834_Screenshot_20251119_192133_GameNative.jpg`) shows the game log repeatedly saying it is loading from Steam Cloud, but cannot open `rep+persistentgamedata1.dat` / related files and falls back to a clean save state. That is strong evidence for **"files exist / metadata exists, but runtime path or expected file set is still wrong"**.
- **Documents / My Games cluster:** a screenshot (`1440872235328868405_Screenshot_20251119_171029_Discord.jpg`) from earlier discussion ties repeated failures to games storing saves under **Documents/My Games**, including Stick of Truth and SteamWorld titles.
- **Portal 2 case/path anomaly:** users reported seeing saves in both `A:/portal2/SAVE` and `A:/portal2/save`, while the game did not use them. This is direct evidence for a **case-sensitive path mismatch** class.
- **Cult of the Lamb mismatch:** a Steam remote storage screenshot (`1450858255176699975_image0.jpg`) shows Steam thinks saves live under **`GameInstall/saves/*.json`**. Thread participants repeatedly reported GameNative behaving as if that were the live path while the actual game runtime expects LocalLow/vendor-style layout. This lines up with the later `rootoverrides` / `pathtransforms` work.
- **Dragon Quest III partial upload evidence:** a remote storage screenshot (`1458856185896898610_Screenshot_2026-01-08_110736.png`) shows multiple files in Steam Cloud (`AutoSaveData.sav`, `ContinueSaveData.sav`, `SaveData_0.sav`, `SystemData_0.sav`), while the thread earlier had logs suggesting only `SystemData_0.sav` uploaded. This is direct evidence for a **partial upload / wrong cloud key set** failure mode.
- **Sonic Mania upload-not-started evidence:** screenshot `1477020672109707405_image-6.png` shows Steam saying **"Cloud Out of Date ... upload not started"**. That matches many user reports where GameNative says saves are up to date while Steam disagrees.
- **Costume Quest 2 stale change-number evidence:** the log attachment `1478242002939150468_app_logs_2026-03-02_23-03-57.txt` shows:
  - `AppChangeNumber: 57 -> 26`
  - `Local change number greater than cloud 57 > 26`
  - result `UnknownFail`
  This is especially important because current code still treats this as a scenario that "should not happen," yet the thread contains concrete runtime evidence that it does happen.

### Failure buckets seen repeatedly

#### 1. Wrong local save path / wrong root mapping
Representative reports:
- Binding of Isaac
- SteamWorld titles
- Portal 2
- Blue Prince
- Dragon's Dogma / Dark Souls PTDE
- Blue Revolver / Return to Monkey Island class (from PR discussion)

Likely causes:
- missing handling for UFS `rootoverrides`
- missing `pathtransforms`
- incomplete prefix handling for some Steam metadata shapes
- case-sensitive filesystem mismatches

#### 2. Files present, but game cannot read them
Representative reports:
- Binding of Isaac
- Rogue Prince of Persia
- New Star GP
- Persona 5 Tactica
- Portal 2

Likely causes:
- runtime working-directory mismatch (`ExeRunDir` class)
- game expects different live folder than raw cloud transport folder
- case-sensitive or path-shape mismatch even when files were downloaded

#### 3. Download works better than upload
Representative reports:
- Witcher 3
- Stardew Valley
- Rhythm Doctor
- Astroneer
- Fields of Mistria
- Dragon Quest III
- Costume Quest 2
- Sonic Mania

Likely causes:
- exit sync not triggering or not being observable enough
- stale / inconsistent local-vs-cloud change-number state
- game writes saves after GameNative’s upload decision point
- wrong cloud-key construction for multi-file or remapped save paths

#### 4. Conflict / pending-state / stale cloud bookkeeping
Representative reports:
- Costume Quest / Costume Quest 2
- Raccoin demo conflict message
- reports of force sync downloading the wrong side
- reports of Steam sign-out or session replacement leading to save confusion

Likely causes:
- cloud bookkeeping cleared too aggressively on auth/session loss (partially addressed upstream)
- "local change number > cloud change number" not handled as a recoverable state
- lack of explicit upload-only / download-only manual controls in the UI

#### 5. Users asking for safety rails, not just root-cause fixes
Recurring requests:
- disable cloud sync for a problem game
- upload-only and download-only actions
- import / export save files manually
- backup before overwrite
- easier access to Steam remote storage page

## Code review

### What current `upstream/master` already covers
- `SteamUtils.writeColdClientIni()` now writes a non-empty `ExeRunDir` pointing at the game root.
  - File: `app/src/main/java/app/gamenative/utils/SteamUtils.kt`
  - This means the `#775` working-directory fix has already landed upstream since older research was written.
- `SteamService.beginLaunchApp()`, `forceSyncUserFiles()`, and `closeApp()` now retry `AsyncJobFailedException` up to 3 times.
  - File: `app/src/main/java/app/gamenative/service/SteamService.kt`
- Cloud sync state is preserved more carefully across auth loss.
  - File: `app/src/main/java/app/gamenative/service/SteamService.kt`
- Browse-online-saves shortcut is already in the Steam app menu.
  - Files:
    - `app/src/main/java/app/gamenative/ui/enums/AppOptionMenuType.kt`
    - `app/src/main/java/app/gamenative/ui/screen/library/appscreen/SteamAppScreen.kt`

### Important gaps still visible in current code

#### 1. `rootoverrides` and `pathtransforms` are still not parsed on master
- File inspected: `app/src/main/java/app/gamenative/utils/KeyValueUtils.kt`
- Current `generateSteamApp()` only reads `ufs.savefiles`; it does **not** parse:
  - `rootoverrides`
  - `pathtransforms`
  - per-platform filtering for save entries
- Repository search on current master also shows no active `uploadRoot`, `cloudRoot`, `uploadPath`, `cloudPath`, or `ufsParseVersion` fields from PR `#839`.
- This leaves a large class of thread issues unsolved.

#### 2. Current Steam cloud code still has no Ludusavi fallback
- Repository search on current master found no active `ludusavi` implementation.
- That means titles where Steam metadata is incomplete still rely entirely on Steam’s parsed UFS data or the very limited no-UFS recursive fallback.

#### 3. The special per-game save mapping system exists, but is barely populated
- Files:
  - `app/src/main/java/app/gamenative/utils/SteamUtils.kt`
  - `app/src/main/java/app/gamenative/enums/SpecialGameSaveMapping.kt`
- The symlink framework from PR `#441` exists, but the registry currently contains only **one** mapping (`The First Berserker: Khazan`).
- That is useful proof of concept, but far too narrow for the volume of thread reports.

#### 4. The UI exposes only a generic "Force cloud sync" even though the lower layers already support more nuanced behavior
- `SteamService.forceSyncUserFiles()` already accepts:
  - `preferredSave: SaveLocation`
  - `overrideLocalChangeNumber`
- `PluviaMain` already uses `SaveLocation.Local` / `SaveLocation.Remote` in conflict flows.
- But `SteamAppScreen` currently only wires a single generic `ForceCloudSync` menu action.
- Meanwhile, `AppOptionMenuType` still defines:
  - `ForceDownloadRemote`
  - `ForceUploadLocal`
- and `GameOptionsPanel` groups those under cloud saves,
- yet `SteamAppScreen` does **not** actually add them as menu options.
- Conclusion: **upload-only / download-only controls are partially scaffolded in code but not exposed**. This is an underused solution path strongly aligned with user requests in the thread.

#### 5. "Local change number greater than cloud" is still treated as impossible, but thread logs prove it happens
- File: `app/src/main/java/app/gamenative/service/SteamAutoCloud.kt`
- Current branch logic:
  - `local < cloud` → download/conflict branch
  - `local == cloud` → compare hashes / maybe upload
  - `local > cloud` → log error and return `UnknownFail`
- The thread’s Costume Quest 2 logs show exactly this supposedly-impossible case in real use.
- That suggests a real remaining bug class:
  - stale local DB state after crashes or interrupted syncs
  - cloud bookkeeping drift
  - update/verify paths leaving local change numbers ahead
- This branch likely needs an explicit recovery path instead of hard-failing.

#### 6. Exit upload observability is still weak
- `SteamService.closeApp()` performs sync and signals `signalAppExitSyncDone(...)`, but does not return a rich result to the UI.
- Thread users repeatedly described uploads silently not happening or Steam still showing stale timestamps.
- This is partly a root-cause problem and partly a product-feedback problem.

## Candidate solutions / gaps

### High-confidence solutions already discovered but not fully landed
1. **Merge or recreate PR #839**
   - Highest-value remaining engineering fix.
   - Best fit for Cult of the Lamb, Blue Revolver, Return to Monkey Island, Vampire Survivors, JellyCar Worlds, and similar manifest-remap cases.

2. **Merge or recreate PR #941**
   - Likely fixes a separate but real class of `SAVE/save`, `LocalLow/locallow`, and duplicate-dir problems.
   - Especially relevant where thread reports show paths differing only by case.

3. **Ship local-only mode (PR #596)**
   - Not a correctness fix, but a strong safety valve.
   - Valuable for first-install overwrite fears, unstable upload cases, and games still under investigation.

4. **Ship manual save import/export (PR #966)**
   - Also not a root-cause fix, but directly solves the user need for recovery and controlled transfer.

### Solutions that appear underused / half-finished in current code
5. **Expose upload-only and download-only sync actions in the UI**
   - The enums and grouping already exist.
   - Service-layer knobs already exist.
   - The thread repeatedly asks for exactly this behavior because "Force cloud sync" is too ambiguous and sometimes destructive.
   - This is one of the clearest undiscovered product-level improvements still hiding in the codebase.

6. **Handle `localChangeNumber > cloudChangeNumber` as recoverable state instead of `UnknownFail`**
   - The thread provides direct logs proving this state occurs.
   - Possible handling options:
     - treat it as conflict and ask local vs remote
     - allow explicit local-preferred upload
     - reset cached change number and re-fetch cloud state before deciding
   - This looks like an uncovered correctness gap, not just UX.

### Plausible but lower-confidence next-step ideas
7. **Revive a smaller Ludusavi fallback for incomplete-UFS titles**
   - Best reserved for games where Steam metadata is provably incomplete, not as a blanket replacement.
   - Could be opt-in or auto-fallback only when UFS returns partial/empty patterns.

8. **Expand the special-game save-mapping registry beyond one title**
   - Useful as a tactical fix path for stubborn runtime-path games.
   - More of a stopgap than a scalable long-term answer.

## Known findings vs hypotheses

### Known from Discord / logs / screenshots
- Steam cloud failures span many months and many games.
- Upload-side failures remained common even after download-side improvements.
- Path mismatch is a major class of failure.
- Case-only folder differences occur in real user reports.
- `local change number > cloud change number` happens in production.
- Users repeatedly want manual directional sync and manual save transfer tools.

### Known from code
- `ExeRunDir` fix is already landed upstream.
- `rootoverrides` / `pathtransforms` support is **not** landed upstream.
- No Ludusavi integration exists on current master.
- A game-specific mapping framework exists but is barely populated.
- Directional sync actions are partially scaffolded but not wired into the Steam app menu.
- Current code still hard-fails on `local > cloud` change-number state.

### Hypotheses / inferences
- Some games in the thread likely depend on Steam Cloud API behavior or metadata semantics not fully represented by the parsed UFS data alone.
- A chunk of the remaining upload-side complaints may be secondary effects of stale bookkeeping, late save writes, or wrong cloud-key construction rather than raw network/upload failure.
- The best remaining fix path is probably **not one PR**, but a combination of:
  - PR `#839`
  - PR `#941`
  - directional manual sync controls
  - local-only / import-export safety tooling

## Opportunities not already in code or current open PRs

These are the best remaining opportunities I found that do **not** appear to already exist in current `upstream/master`, and are **not** the focus of an open PR.

### 1. Treat `local change number > cloud change number` as a recoverable state
- Current code in `SteamAutoCloud.kt` treats this as impossible and returns `UnknownFail`.
- Thread logs prove it happens in production.
- Opportunity:
  - invalidate that app's cached file list / change number
  - force a full cloud re-fetch
  - if both sides still diverge, route into a normal local-vs-remote conflict choice instead of a hard failure
- This is one of the clearest correctness gaps not covered by current code or open PRs.

### 2. Add a safety backup / rollback layer before destructive sync operations
- Repeated thread fear: force sync or conflict resolution can overwrite good saves with bad/empty ones.
- Opportunity:
  - snapshot local save roots before download/overwrite
  - keep a small rotating history per game
  - surface a one-tap "restore previous local backup" action after bad syncs
- This is different from PR `#966` import/export: it would be **automatic**, local, and tied to sync risk.

### 3. Add first-run / first-sync protection against uploading empty state
- Several reports describe first install or early runs replacing valid cloud history with empty local state.
- Opportunity:
  - mark a game/container as "cloud not yet trusted / not yet initialized"
  - refuse upload-only behavior until one of these happens:
    - successful initial cloud pull
    - user confirms they want local to become the source of truth
    - user imports saves manually
- This would specifically reduce the "new install wiped my Steam save" class.

### 4. Add delayed / stability-aware exit sync for games that write saves late
- Multiple thread workarounds involve waiting at the main menu or after quit before forcing sync.
- Opportunity:
  - watch candidate save roots for a short post-exit stabilization window
  - only upload after timestamps stop changing
  - optionally retry one extra scan if files changed during teardown
- This targets games whose save writes happen slightly after the process appears to exit.

### 5. Add Steam-cloud-specific case-insensitive save-path resolution inside `SteamAutoCloud`
- Open PR `#941` improves case-sensitive behavior for Steam depot downloads and Epic/GOG cloud save paths.
- But current `SteamAutoCloud` local save discovery still builds exact paths from parsed metadata and scans them directly.
- Opportunity:
  - resolve the actual on-disk casing for Steam save roots/subpaths before scanning or writing
  - reduce failures like `SAVE` vs `save`, `LocalLow` vs `locallow`, etc., specifically in the Steam cloud sync pipeline
- This appears adjacent to `#941`, but not actually covered by it.

### 6. Detect probable incomplete-manifest / hybrid Steam Cloud API titles automatically
- The thread suggests some games use a mix of Auto-Cloud metadata plus game-side Steam Cloud API behavior.
- Opportunity:
  - when Steam reports cloud files but local pattern matching finds only a suspicious subset, flag the app as "manifest may be incomplete"
  - expand scanning heuristics or prompt the user before claiming "UpToDate"
  - optionally persist a per-game heuristic state instead of requiring a full Ludusavi integration first
- This would be a middle ground between today's strict UFS dependence and the abandoned Ludusavi draft.

### 7. Improve post-sync observability with a per-game sync journal
- Today many thread reports amount to "GameNative said up to date, but Steam disagrees."
- Opportunity:
  - persist last sync result, timestamps, file counts, uploaded/downloaded files, and error class per game
  - expose a small "last sync details" sheet in the app
- This would not fix root causes directly, but it would make future cloud-save bugs dramatically easier to diagnose and safer for users.

## Bottom line
The Discord thread is best understood as a **cluster of Steam cloud issues**, not a single bug. Current `upstream/master` has already fixed some important pieces (`ExeRunDir`, auth-loss preservation, retry logic, browse-online-saves), but the biggest remaining correctness gap is still **Windows UFS remapping support** (`rootoverrides`, `pathtransforms`, cache invalidation) represented by **PR #839**. A second major gap is **case-sensitive path handling**, represented by **PR #941**.

Beyond correctness, the thread makes it very clear the product still needs safer manual controls. The codebase already contains the beginnings of that direction: service-layer support for local-vs-remote preference, plus dormant UI enum entries for **force download remote** and **force upload local**. Exposing those, along with local-only mode and save import/export, would materially reduce user risk even before every root-cause bug is solved.
